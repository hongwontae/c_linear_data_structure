1. 데이터 추가/삭제와 인덱스 업데이트
    1-1. 데이터 추가, 삭제, 업데이트 시 인덱스도 함께 변경
    1-2. 이미 정렬된 데이터에 새 데이터를 추가하는 경우 전체 데이터를 다시 정렬할 것인지 고려
    1-3. 삽입 정렬 방식 사용에 대한 고려


2. 여러 인덱스 생성
    2-1. 구조체 멤버가 여러 개일 때 각 멤버를 기준으로 정렬
    2-2. 인덱스가 여러 개면 데이터 추가, 삭제, 변경 시 함께 업데이트 해야 할 인덱스가 늘어나면서 오버헤드 증가
    2-3. 인덱스가 꼭 필요한 것인지 고려


3. 개념 분리
    3-1. int a = 10; int a_a = &a;
        => 자료형 선언은 값에 대한 타입 선언입니다.
        => a의 값은 int / a의 주소 자체의 타입은? -> int *
        => a_a의 값은 int * / a_a 주소 자체의 타입은 -> int **
    
    3-2. USERDATA ** pNodePtrList = malloc(sizeof(USERDATA*) * cnt);
        => 망상을 하면 안됩니다.
        => pNodePtrList 주소의 타입은 USERDATA *** / 값의 타입은 USERDATA **
        => 인덱스 접근시 USERDATA * 입니다.
        => 즉, 인덱스 접근은 값의 타입을 한 단계 내린 느낌입니다.
    
    3-3. 포인터 연산 시 이동하는 바이트는 접근하는 값의 타입에 의해서 결정됩니다.
        => USERDATA ** pp; pp[1] -> pp[2] -> USERDATA * 만큼 이동
        => pp[0]의 값은 USERDATA * -> 이 타입만큼 움직임


4. 이중 포인터를 사용하는 이유
    => 메모리 절약: 구조체 전체를 복사하지 않고 포인터 크기만큼만 저장해.
    => 정렬 비용 감소: 구조체 전체 대신 포인터만 교환하면 돼.
    => 원본 데이터 유지: 나이순으로 정렬해도 연결 리스트 자체의 순서는 바뀌지 않아.
    => 원본 수정 가능: aList[i]->age처럼 접근하면 원래 연결 리스트에 있는 구조체를 수정하게 돼.
    
    => USERDATA *으로 처리했다면?
    => USERDATA 주소를 값으로 받을 수 있으나 하나만 받을 수 있는 형태입니다.
    => 즉, 배열로 모으기 위해서는 값 자체를 사용해서 연결해야 합니다. -> 그럼 기존의 연결 리스트와 다른 것입니다.
